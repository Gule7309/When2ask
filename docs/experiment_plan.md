# Experiment 1: Candidate-set incompleteness

## 1. Question

SAGE-Agent represents uncertainty over a finite set of candidate tool calls generated by an LLM. This experiment asks whether that uncertainty remains a reliable action signal when the intended tool-call interpretation is absent from the candidate set.

The intended contribution of this experiment is mechanistic. We are not trying to show that candidate generation can make mistakes; that is expected. The stronger question is whether SAGE's downstream confidence reflects *candidate-set incompleteness* or can remain high after the correct hypothesis has already been excluded.

## 2. Hypotheses

### H1: candidate completeness

Let `GT-in-C` indicate that at least one candidate is compatible with the current ground-truth tool call. We expect:

`Coverage(GT-in-C) > Coverage(GT-not-in-C)`.

This is mainly a diagnostic hypothesis and is not sufficient by itself to establish a failure in the uncertainty formulation.

### H2: overconfidence under omission

When `GT-not-in-C`, the maximum SAGE candidate confidence may remain high. The primary failure event is:

`wrong execution AND max_candidate_confidence >= tau`.

We will report HCWE over a threshold sweep rather than selecting a favorable threshold after seeing results.

### H3: causal effect of candidate availability

For the same benchmark item, forcing the ground-truth candidate out of the set should increase error, while adding a compatible partial candidate to an incomplete set should recover performance. The strongest evidence is a paired Natural / Oracle-complete / Forced-miss contrast.

### H4: open-world correction

This is a follow-up hypothesis only. We will not implement an `UNKNOWN` mass or candidate-coverage estimator until H1–H3 have been evaluated.

## 3. Unit of analysis

The unit of analysis is a SAGE decision point associated with one ground-truth tool call. Multi-call benchmark scenarios must be aligned by request/turn before they enter the intervention study. A sample-level aggregate may be reported secondarily, but interventions must not mix candidates from different ground-truth turns.

## 4. Ground-truth compatibility

A candidate `c` is GT-compatible when:

1. `c.tool_name == gt.tool_name`;
2. every argument specified by `c` exists in the ground-truth call and matches its value;
3. missing arguments or arguments represented as `<UNK>` are allowed.

This is deliberately weaker than execution correctness. It asks whether the candidate can still represent the intended tool call before clarification completes.

For Oracle-complete, hidden ground-truth argument values must **not** be inserted. Arguments not independently observed by the candidate generator are represented as `<UNK>`.

## 5. Conditions

### Natural

Use the candidate set emitted by the reproduced SAGE candidate-generation stage.

### Oracle-complete

If Natural does not contain a GT-compatible candidate, append a GT-compatible partial candidate. The initial implementation permits an increased set size so that the manipulation is explicit. A size-matched version will be added as a robustness check if set size materially changes downstream behavior.

### Forced-miss

Remove every GT-compatible candidate. To avoid turning candidate count into the treatment, the main forced-miss condition should insert a decoy candidate when a suitable one can be constructed. Decoys should be matched on the following features as closely as possible:

- number of required arguments;
- number of `<UNK>` arguments;
- finite-domain sizes of unresolved arguments;
- semantic/tool-family proximity.

Decoy generation and matching quality must be logged. Samples without a defensible decoy should be excluded from the size-matched forced-miss analysis and reported separately rather than filled with arbitrary tools.

## 6. Dataset and model controls

### Primary dataset

ClarifyBench-Ambiguous.

### Primary simulator

A deterministic oracle simulator is preferred for the first mechanistic run. It should answer only the targeted ground-truth aspect and should not volunteer future intent. The paper-style LLM simulator is a robustness condition, not the primary causal run.

### Base model

Start with one paper-supported model/configuration to validate the mechanism. Cross-model replication follows only after the intervention pipeline is stable.

### Fixed paper hyperparameters

Where specified by the paper:

- `lambda = 0.5`
- `alpha = 0.1`
- `epsilon = 1e-4`
- main-comparison temperature `= 0.5`

The numerical execution threshold is not treated as known. We predeclare a sensitivity sweep:

`tau_exec in {0.5, 0.6, 0.7, 0.8, 0.9}`.

Candidate-set size will be studied at:

`N in {1, 3, 5, 10}`

when the candidate generator supports controlled `N`.

## 7. Metrics

### Paper-compatible metrics

- Coverage
- Tool Match Rate (TMR)
- Parameter Match Rate (PMR)
- average clarification questions (#Q)

### Diagnostic metrics

**Candidate recall**

`mean[GT-compatible candidate exists]`

**Conditional execution accuracy**

Report separately for `GT-in-C` and `GT-not-in-C`.

**High-confidence wrong execution rate (HCWE)**

For threshold `tau`:

`mean[wrong execution AND executed candidate confidence >= tau]`.

The denominator is all evaluated decision points. A conditional version among executions may also be shown, but it must be labeled separately.

**Oracle recovery gap**

Difference between Oracle-complete and Natural on paired examples that were incomplete under Natural.

**Calibration**

Reliability curves for maximum candidate confidence versus empirical correctness, stratified by candidate-set completeness.

## 8. Statistical analysis

Natural, Oracle-complete, and Forced-miss are paired at the item level.

- binary outcomes such as exact coverage: McNemar test plus paired bootstrap confidence interval for the absolute difference;
- continuous/count outcomes such as PMR or #Q: paired bootstrap interval; Wilcoxon signed-rank may be reported as a non-parametric secondary test;
- calibration: reliability diagrams and expected calibration error, stratified by candidate presence, with bootstrap intervals where feasible.

The main report should emphasize effect sizes and intervals rather than only p-values.

## 9. Evidence thresholds

### Strong support for the attack

All of the following should hold:

1. correctness falls substantially when the GT candidate is absent;
2. maximum candidate confidence does not fall enough to track this loss in correctness;
3. HCWE increases in the Forced-miss condition;
4. Oracle-complete materially restores performance on naturally incomplete or forced-miss cases.

### Partial support

Candidate omission reduces accuracy, but confidence falls and clarification behavior adjusts appropriately. This would indicate a candidate-generation bottleneck without strong evidence that SAGE's uncertainty is misleading.

### Attack not supported

When the intended candidate is absent, SAGE reliably lowers confidence, avoids premature execution, and/or regenerates candidates so that final behavior remains calibrated. In that case we should move to another attack rather than modify the method to solve a failure we did not observe.

## 10. Execution order

1. reproduce the public ClarifyBench sample harness;
2. instrument candidate generation and structured confidence;
3. measure Natural candidate recall on a small diagnostic subset;
4. manually audit GT-compatibility labels and turn alignment;
5. run paired Natural / Oracle-complete / Forced-miss on the subset;
6. freeze intervention code and analysis schema;
7. run the full Ambiguous split;
8. only then consider an open-world modification.
